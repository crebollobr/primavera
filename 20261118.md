# Projeto Final — Meu Site no Ar

> **Você não precisa ser especialista. Precisa colocar algo seu no ar.**

Durante o curso, você saiu do terminal Linux e chegou até uma página publicada no Kubernetes. O projeto final é a prova de que você consegue levar uma ideia do zero até o navegador de qualquer pessoa.

Você vai criar uma **página pessoal** e publicá-la em:

```text
https://curso.chr.eti.br/alunoXX/
```

Simples, mas real: o link funciona, pode ser compartilhado e fica no ar. O objetivo não é fazer um site profissional. É mostrar que você domina o caminho:

```text
YAML -> Deployment -> Pods -> Service -> Ingress -> navegador
```

---

## 1. A missão

Crie uma página com a sua identidade e publique no cluster da turma.

A página deve ter:

- **Seu nome** (ou apelido) e uma frase curta sobre você.
- **Minha jornada DevOps:** pelo menos 3 momentos do curso.
  - Exemplos: primeiro comando no Linux, primeiro container, primeiro Pod, primeiro deploy.
- **3 coisas que eu aprendi:** 3 comandos ou conceitos com uma explicação curta.
  - Exemplos: `docker ps`, `kubectl get pods`, `kubectl describe`, labels, Service, Ingress.
- **Recado para a turma:** uma frase, um conselho ou um agradecimento.
- **Rodapé:** `Deploy por alunoXX em DD/MM/AAAA`.

Regras:

- A página deve ser servida pelo **nginx** a partir de um **ConfigMap**.
- O Deployment deve ter **2 réplicas**.
- O acesso deve passar por **Service ClusterIP + Ingress**.
- Use **CSS inline** no HTML. Não dependa de CDN, imagem externa ou internet.
- O conteúdo precisa ser seu. Pode se inspirar no layout de um colega, mas não copie a página.
- A página deve continuar no ar depois da entrega. **Não apague os objetos** no final.

## 3. A arquitetura

```text
Navegador
  │  https://curso.chr.eti.br/alunoXX/
  ▼
Proxy reverso (professor)
  │  encaminha para o Ingress Controller
  ▼
Ingress Controller
  │  regra: host curso.chr.eti.br + path /alunoXX
  ▼
Service svc-alunoXX (ClusterIP)
  │  balanceia entre os Endpoints
  ├── Pod deploy-alunoXX-aaaaa
  └── Pod deploy-alunoXX-bbbbb
        │
        └── ConfigMap site-alunoXX
              └── /usr/share/nginx/html/alunoXX/index.html
```

| Objeto | O que faz no projeto |
| --- | --- |
| **ConfigMap** | Guarda o `index.html` da sua página. |
| **Deployment** | Mantém 2 Pods nginx rodando e recria se um cair. |
| **Service** | Dá um endereço fixo e balanceia para os 2 Pods. |
| **Ingress** | Publica o path `/alunoXX` no host `curso.chr.eti.br`. |
| **Pod** | Executa o nginx que entrega o HTML. |

## 4. O modelo incompleto

O modelo está no repositório:

```text
projeto-final/modelo-site.yaml
```

Ele tem **4 blocos obrigatórios**, cada um com comentários:

1. **ConfigMap** — o HTML da página.
2. **Deployment** — 2 réplicas do nginx.
3. **Service** — o endereço estável.
4. **Ingress** — a publicação em `/alunoXX`.

O arquivo está **incompleto de propósito**:

- `alunoXX` deve virar o seu número (`aluno01` ... `aluno20`).
- `SEU NOME`, `SUA FRASE` e os `TODO` do HTML devem ser preenchidos por você.
- A classe do Ingress deve ser conferida no seu cluster.

> **Não apague os comentários do YAML.** Eles explicam o que cada bloco faz e ajudam na apresentação.

### 4.1 Baixar ou copiar o modelo

O professor pode disponibilizar o arquivo no servidor:

```bash
# Copie o modelo para a sua pasta de trabalho.
cp /tmp/modelo-site.yaml .
```

Se o repositório já estiver publicado no GitHub, você também pode baixar:

```bash
# Baixa o modelo direto do repositório do curso.
curl -fsSL https://raw.githubusercontent.com/crebollobr/primavera/main/projeto-final/modelo-site.yaml -o modelo-site.yaml
```

Confira o conteúdo:

```bash
# Mostra o modelo com os comentários.
cat modelo-site.yaml
```

### 4.2 Gerar o seu arquivo

```bash
# 1. Defina o seu número. Troque alunoXX pelo número que o professor informou.
export ALUNO=alunoXX

# 2. Confira se a variável está certa.
echo $ALUNO

# 3. Troque todas as ocorrências de alunoXX pelo seu número.
sed "s/alunoXX/$ALUNO/g" modelo-site.yaml > site-$ALUNO.yaml

# 4. Confira o nome dos objetos e o path do Ingress.
grep -E "name:|path:|mountPath:" site-$ALUNO.yaml
```

O `sed` troca o nome dos objetos, as labels, o path do Ingress e a pasta dentro do nginx. Mesmo assim, **abra o arquivo e confira**.

### 4.3 Escrever o conteúdo

```bash
# Abra o arquivo no editor.
nano site-$ALUNO.yaml
```

Dentro do bloco `data: index.html: |`, substitua:

- `SEU NOME` pelo seu nome.
- `SUA FRASE EM UMA LINHA` por uma frase sua.
- Os `<!-- TODO: ... -->` pelo conteúdo real.
- As cores do bloco `<style>` se quiser.
- `<!-- TODO: DD/MM/AAAA -->` pela data do deploy.

> O HTML fica dentro do YAML. A indentação importa: mantenha o HTML com a mesma indentação do modelo. Se o YAML quebrar, o `kubectl apply` vai avisar.

### 4.4 Conferir a classe do Ingress

```bash
# O Ingress precisa de uma classe válida.
kubectl get ingressclass
```

No laboratório, o normal é aparecer `public`. Se aparecer `nginx`, edite o YAML:

```bash
# Se a classe do seu cluster for nginx, troque public por nginx.
sed -i 's/ingressClassName: public/ingressClassName: nginx/' site-$ALUNO.yaml

# Confira o resultado.
grep ingressClassName site-$ALUNO.yaml
```

### 4.5 Aplicar no cluster

```bash
# Cria o ConfigMap, o Deployment, o Service e o Ingress de uma vez.
kubectl apply -f site-$ALUNO.yaml
```

A saída deve mostrar os quatro objetos criados (ou configurados):

```text
configmap/site-alunoXX created
deployment.apps/deploy-alunoXX created
service/svc-alunoXX created
ingress.networking.k8s.io/ingress-alunoXX created
```

### 4.6 Acompanhar os Pods

```bash
# Mostra os Pods do seu Deployment. Devem aparecer 2.
kubectl get pods -l app=app-$ALUNO

# Acompanha a criação em tempo real. Use Ctrl+C para sair.
kubectl get pods -l app=app-$ALUNO -w
```

O esperado é:

```text
NAME                              READY   STATUS    RESTARTS
deploy-alunoXX-aaaaa              1/1     Running   0
deploy-alunoXX-bbbbb              1/1     Running   0
```

### 4.7 Conferir Service, Endpoints e Ingress

```bash
# O Service deve ter 2 Endpoints (um para cada Pod).
kubectl get svc svc-$ALUNO
kubectl get endpoints svc-$ALUNO

# O Ingress deve mostrar o host e o path /alunoXX.
kubectl get ingress ingress-$ALUNO
kubectl describe ingress ingress-$ALUNO
```

Se o `get endpoints` mostrar `<none>`, o Service não encontrou os Pods. Confira as labels:

```bash
# As labels dos Pods precisam ser iguais ao selector do Service.
kubectl get pods -l app=app-$ALUNO --show-labels
```

### 4.8 Testar por dentro do cluster

Antes de testar pela internet, teste o Service diretamente:

```bash
# Sobe um Pod temporário e faz uma requisição para o Service.
kubectl run teste-$ALUNO --rm -it --image=busybox:1.28 --restart=Never -- wget -qO- http://svc-$ALUNO
```

Deve aparecer o HTML da sua página. Isso prova que o DNS interno e o Service estão funcionando.

### 4.9 Testar pela URL pública

```bash
# Mostra o código HTTP. O esperado é 200.
curl -s -o /dev/null -w "%{http_code}\n" https://curso.chr.eti.br/$ALUNO/

# Mostra o começo do HTML retornado.
curl -s https://curso.chr.eti.br/$ALUNO/ | head

# Se vier 301, siga o redirecionamento.
curl -sL https://curso.chr.eti.br/$ALUNO/ | head
```

Acesse também no navegador:

```text
https://curso.chr.eti.br/alunoXX/
```

> Use a barra no final. Sem ela, o nginx pode responder `301` para `/alunoXX/`.

### 4.10 Provar o self-healing

Abra **dois terminais**. No segundo, faça o `export ALUNO=alunoXX` de novo.

```bash
# Terminal 1 — acompanha os Pods em tempo real.
kubectl get pods -l app=app-$ALUNO -w
```

```bash
# Terminal 2 — apaga um Pod de cada vez.
POD=$(kubectl get pods -l app=app-$ALUNO -o jsonpath='{.items[0].metadata.name}')
echo $POD
kubectl delete pod $POD
```

No terminal 1, você deve ver o Pod apagado sair e um novo Pod ser criado pelo Deployment. O site continua no ar porque o Service aponta para os Endpoints, e ainda existe outra réplica.

Use `Ctrl+C` para sair do `-w`.

## 7. Desafio extra — PVC

Este desafio é **opcional**. Ele usa o que vimos na aula de Storage.

Objetivo: guardar um `recado.txt` em um volume que sobrevive ao Pod e linkar esse recado na página.

### 7.1 Criar o PVC

Crie o PVC já com o seu número no nome:

```bash
# Cria o arquivo pvc-alunoXX.yaml com o PVC.
cat > pvc-$ALUNO.yaml <<EOF
# PVC: um volume de 100Mi que sobrevive à recriação dos Pods.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-$ALUNO
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 100Mi
EOF

# Aplique o PVC.
kubectl apply -f pvc-$ALUNO.yaml

# Confira o status. Pode ficar Pending até o Deployment usar o volume.
kubectl get pvc pvc-$ALUNO
```

> A StorageClass do laboratório usa `WaitForFirstConsumer`: o PVC só é vinculado depois que um Pod que o utiliza é agendado. Por isso o `Pending` aqui é normal; ele deve virar `Bound` depois do passo 7.2.

### 7.2 Montar o PVC no Deployment

No `site-$ALUNO.yaml`, altere os `volumeMounts` e os `volumes` do Deployment:

```yaml
          volumeMounts:
            # O ConfigMap monta apenas o index.html, via subPath.
            - name: site
              mountPath: /usr/share/nginx/html/alunoXX/index.html
              subPath: index.html
            # O PVC monta a pasta recados ao lado do index.html.
            - name: recados
              mountPath: /usr/share/nginx/html/alunoXX/recados
      volumes:
        - name: site
          configMap:
            name: site-alunoXX
        - name: recados
          persistentVolumeClaim:
            claimName: pvc-alunoXX
```

> Troque `alunoXX` pelo seu número nos quatro lugares. O `subPath` evita conflito entre o arquivo do ConfigMap e a pasta do PVC.
>
> Como o `subPath` não atualiza sozinho quando o ConfigMap muda, depois de alterar o HTML rode `kubectl rollout restart deployment/deploy-$ALUNO` para os Pods lerem o novo conteúdo.

Aplique de novo:

```bash
# Atualiza o Deployment com o novo volume.
kubectl apply -f site-$ALUNO.yaml

# Acompanha o rollout.
kubectl rollout status deployment/deploy-$ALUNO

# Agora o PVC deve estar Bound.
kubectl get pvc pvc-$ALUNO
```

### 7.3 Escrever o recado

```bash
# Escreve o arquivo dentro do PVC, via Pod.
kubectl exec deploy/deploy-$ALUNO -- sh -c \
  "echo 'Meu recado para a turma' > /usr/share/nginx/html/$ALUNO/recados/recado.txt"

# Confere o conteúdo.
kubectl exec deploy/deploy-$ALUNO -- cat /usr/share/nginx/html/$ALUNO/recados/recado.txt
```

Coloque o link no HTML:

```html
<a href="recados/recado.txt">Ler meu recado</a>
```

Teste:

```bash
# O recado deve aparecer.
curl -s https://curso.chr.eti.br/$ALUNO/recados/recado.txt
```

Agora apague um Pod e confira que o arquivo continua lá:

```bash
# O PVC não é apagado quando o Pod é recriado.
kubectl delete pod $(kubectl get pods -l app=app-$ALUNO -o jsonpath='{.items[0].metadata.name}')
kubectl get pods -l app=app-$ALUNO -w
curl -s https://curso.chr.eti.br/$ALUNO/recados/recado.txt
```

> No laboratório o cluster é de um nó só, então o PVC `ReadWriteOnce` funciona com as 2 réplicas. Em um cluster com vários nós, um PVC RWO pode prender os Pods ao nó onde o volume foi criado.

## 9. Problemas comuns

| Sintoma | Causa provável | O que verificar |
| --- | --- | --- |
| `404` do nginx | Path do Ingress não combina com a pasta do HTML | `mountPath`, `path` e `ls /usr/share/nginx/html/alunoXX`. |
| `503 Service Unavailable` | Service sem Endpoints | Labels do Pod, `kubectl get endpoints`. |
| `502 Bad Gateway` | Ingress não chega no Service | `port`/`targetPort` e Endpoints. |
| Página padrão do nginx | ConfigMap não foi montado | `volumeMounts`, `volumes` e `kubectl exec ... ls`. |
| Ingress ignorado | Classe errada ou controller ausente | `kubectl get ingressclass`, pods do namespace `ingress`. |
| `301` | URL sem barra no final | Use `/alunoXX/` ou `curl -L`. |
| `ImagePullBackOff` | Imagem não baixou | `kubectl describe pod`, tente `nginx:latest`. |
| `CreateContainerConfigError` | ConfigMap com nome errado | `kubectl describe pod`, nome em `volumes.configMap`. |
| YAML inválido | Indentação quebrada no HTML | `kubectl apply --dry-run=client -f site-$ALUNO.yaml`. |

Para investigar:

```bash
# O básico do diagnóstico.
kubectl get pods -l app=app-$ALUNO
kubectl describe pod <nome-do-pod>
kubectl logs <nome-do-pod>
```

# Kubernetes: Deployment — Réplicas e Autorrecuperação

### 1. O que é um Deployment

Na aula anterior criamos um **Pod** diretamente. Funciona, mas tem um problema: se o Pod morrer (falha, alguém apagou, o nó caiu), **ninguém recria**. A aplicação fica fora do ar.

O **Deployment** resolve isso. Ele é um objeto **declarativo**: você diz *"quero 3 cópias desta aplicação rodando"* e o Kubernetes trabalha continuamente para que a realidade seja igual ao que foi declarado.

```
Deployment  (o que eu quero: imagem nginx, 3 réplicas)
   └── ReplicaSet  (garante que existam exatamente 3 Pods)
         ├── Pod deploy-nome-xxxxx-aaaaa
         ├── Pod deploy-nome-xxxxx-bbbbb
         └── Pod deploy-nome-xxxxx-ccccc
```

* **Réplicas (`spec.replicas`):** quantas cópias idênticas do Pod devem estar rodando.
* **Seletor (`spec.selector.matchLabels`):** como o Deployment reconhece os Pods que são "dele" — pelos *labels*.
* **Template (`spec.template`):** o "molde" do Pod. É praticamente o mesmo YAML do Pod da aula anterior, só que dentro do Deployment.
* **Autorrecuperação (*self-healing*):** se um Pod for apagado ou falhar, o ReplicaSet percebe que existem menos Pods do que o desejado e cria outro automaticamente.

| Pod sozinho                        | Deployment                                  |
| ---------------------------------- | ------------------------------------------- |
| Apagou, acabou                     | Apagou, nasce outro                         |
| Uma única cópia                    | N cópias (réplicas)                         |
| Nome fixo (`pod-nome`)             | Nome gerado (`deploy-nome-89677b9c-h9fhp`)  |
| Escalar = criar outro YAML         | Escalar = mudar um número                   |

> **Importante:** o `label` do template precisa ser **único por aluno** (`app: app-nome`). Se todos usarem o mesmo label, o Service de um aluno vai mandar tráfego para os Pods dos colegas.

### 2. Roteiro Prático de Laboratório

Substitua **`alunoxx`** pelo número definido pelo professor (ex.: `aluno07`).

#### Passo A: Definir a variável do aluno

Assim não precisamos editar o nome em cada comando:

```bash
export ALUNO=alunoxx

echo $ALUNO
```

> Se abrir um novo terminal, execute o `export` de novo.

#### Passo B: Limpar a aula anterior

O Service da aula anterior tem o mesmo nome que vamos usar agora:

```bash
kubectl delete pod pod-$ALUNO --ignore-not-found
kubectl delete service svc-$ALUNO --ignore-not-found
```

#### Passo C: Gerar o seu YAML a partir do template

O template usa a palavra **`nome`**. O `sed` troca todas as ocorrências pelo seu aluno:

```bash
cat /tmp/deployment.yaml

sed "s/nome/$ALUNO/g" /tmp/deployment.yaml > /tmp/$ALUNO-deployment.yaml

cat /tmp/$ALUNO-deployment.yaml
```

O arquivo gerado fica assim (exemplo com `aluno07`):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-aluno07
  labels:
    app: app-aluno07
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app-aluno07
  template:
    metadata:
      labels:
        app: app-aluno07
    spec:
      containers:
        - name: nginx-container
          image: nginx:latest
          ports:
            - containerPort: 80
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: POD_IP
              valueFrom:
                fieldRef:
                  fieldPath: status.podIP
          command: ["/bin/sh", "-c"]
          args:
            - |
              mkdir -p /usr/share/nginx/html/aluno07
              cat > /usr/share/nginx/html/aluno07/index.html <<FIM
              <html>
              <head><meta http-equiv="refresh" content="2"><title>aluno07</title></head>
              <body style="font-family:sans-serif;text-align:center;margin-top:15%">
              <h1>aluno07</h1>
              <h2>Pod: $POD_NAME</h2>
              <p>IP: $POD_IP</p>
              </body>
              </html>
              FIM
              exec nginx -g 'daemon off;'
```

O que há de novo em relação ao Pod:

* `env` com `fieldRef`: o Kubernetes injeta no contêiner o **nome** e o **IP do próprio Pod**.
* `command`/`args`: antes de iniciar o nginx, o contêiner cria uma página que mostra **qual Pod respondeu**. A página recarrega sozinha a cada 2 segundos.
* Não usamos mais `hostPath`: cada réplica gera a sua própria página.

Verificar o conteúdo do arquivo yaml no site https://todiagram.com/editor

#### Passo D: Criar o Deployment e publicar

```bash
# 1. Criar o Deployment
kubectl apply -f /tmp/$ALUNO-deployment.yaml

# 2. Ver o Deployment, o ReplicaSet e o Pod criados
kubectl get deployment deploy-$ALUNO
kubectl get replicaset -l app=app-$ALUNO
kubectl get pods -l app=app-$ALUNO

# 3. Publicar (agora expomos o Deployment, não o Pod)
kubectl expose deployment deploy-$ALUNO --port=80 --target-port=80 --name=svc-$ALUNO

kubectl get svc svc-$ALUNO
kubectl get endpoints svc-$ALUNO
```

Acessar a URL (com a barra no final): **https://curso.chr.eti.br/alunoxx/**

Deve aparecer o nome do único Pod.

#### Passo E: Escalar com `kubectl patch`

O `patch` altera só um campo do objeto que já está rodando, sem editar o YAML:

```bash
# Subir para 3 réplicas
kubectl patch deployment deploy-$ALUNO -p '{"spec":{"replicas":3}}'

kubectl get pods -l app=app-$ALUNO
kubectl get endpoints svc-$ALUNO
```

Volte ao navegador: a cada recarregamento o **nome do Pod muda**. O Service está distribuindo as requisições entre as 3 réplicas.

Para ver pelo terminal:

```bash
for i in $(seq 10); do curl -s https://curso.chr.eti.br/$ALUNO/ | grep "Pod:"; done
```

Experimente outros valores:

```bash
kubectl patch deployment deploy-$ALUNO -p '{"spec":{"replicas":5}}'
kubectl get pods -l app=app-$ALUNO

kubectl patch deployment deploy-$ALUNO -p '{"spec":{"replicas":2}}'
kubectl get pods -l app=app-$ALUNO
```

> Atalho equivalente: `kubectl scale deployment deploy-$ALUNO --replicas=3`

#### Passo F: Testar a autorrecuperação

Abra **dois terminais** (lembre do `export ALUNO=alunoxx` no segundo).

```bash
# Terminal 1 — acompanhar os Pods em tempo real
kubectl get pods -l app=app-$ALUNO -w
```

```bash
# Terminal 2 — apagar um Pod (copie um nome da lista)
kubectl get pods -l app=app-$ALUNO
kubectl delete pod deploy-alunoxx-xxxxxxxxx-xxxxx
```

No terminal 1, o Pod apagado entra em `Terminating` e **imediatamente** nasce outro com nome novo. No navegador, um nome some e aparece outro.

Desafio: apague **todos** os Pods de uma vez e observe:

```bash
kubectl delete pods -l app=app-$ALUNO
kubectl get pods -l app=app-$ALUNO
```

Compare com a aula anterior: quando apagamos o `pod-nome`, ele não voltou.

#### Passo G: Remover após a validação

```bash
kubectl delete -f /tmp/$ALUNO-deployment.yaml
kubectl delete service svc-$ALUNO

# Os Pods somem junto com o Deployment
kubectl get pods -l app=app-$ALUNO
```

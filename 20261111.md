# Kubernetes: Storage — hostPath, volumes e volumeMounts

### 1. O problema: dados dentro do contêiner não sobrevivem

Nas aulas anteriores, o Deployment garantiu que sempre exista um Pod rodando e o Service/Ingress publicou a aplicação. Mas se a página foi criada **dentro do contêiner**, ela desaparece quando o Pod é recriado — o sistema de arquivos do contêiner é descartável.

Para o site sobreviver, os arquivos precisam ficar **fora** do contêiner, em um **volume**.

```
Pod
 └── contêiner nginx
       └── volumeMounts: /usr/share/nginx/html/alunoxx
                 │
                 ▼
            volumes: site
                 │
     ┌───────────┴────────────┐
     ▼                        ▼
 hostPath direto        PVC → PV → pasta no nó
```

Dois conceitos do YAML que já apareceram na aula de Pod:

| Campo | Onde fica | O que faz |
| --- | --- | --- |
| `volumes` | `spec.volumes` (nível do Pod) | Declara a **origem** do armazenamento. |
| `volumeMounts` | `spec.containers[].volumeMounts` (nível do contêiner) | Diz **em qual pasta** do contêiner o volume será montado. |

O mesmo volume pode ser montado em vários contêineres do Pod; cada um pode usar um `mountPath` diferente.

---

### 2. hostPath: o jeito direto (e suas limitações)

Na aula de Pod usamos `hostPath`:

```yaml
spec:
  containers:
    - name: nginx-container
      volumeMounts:
        - name: meu-volume-local
          mountPath: /usr/share/nginx/html/aluno07
  volumes:
    - name: meu-volume-local
      hostPath:
        path: /tmp/aluno07
        type: Directory
```

O Pod monta uma pasta que já existe **no nó** (a máquina onde o Pod está rodando). Tudo que o contêiner gravar em `/usr/share/nginx/html/aluno07` aparece em `/tmp/aluno07` no nó.

Funciona e é ótimo para laboratório. Mas tem problemas:

- O caminho precisa existir no nó e o Pod fica **preso àquele nó**.
- Se o Pod for agendado em outro nó, a pasta não existe lá.
- Não há controle de ciclo de vida, tamanho, permissões ou backup.
- Qualquer Pod que conheça o caminho consegue ler os dados.

Comparando os tipos de volume:

| Tipo | Sobrevive ao Pod? | Escopo |
| --- | --- | --- |
| `emptyDir` | Não | Vive enquanto o Pod existir (bom para cache). |
| `hostPath` | Sim, no mesmo nó | Pasta do nó, escolhida manualmente. |
| PVC/PV | Sim | Abstração do cluster; o Pod não conhece o caminho. |

Para dados de aplicação, o Kubernetes oferece uma abstração melhor: **PV**, **PVC** e **StorageClass**.

---

### 3. PV, PVC e StorageClass

| Objeto | O que é |
| --- | --- |
| **PersistentVolume (PV)** | Um pedaço de armazenamento no cluster (a "vaga" real). |
| **PersistentVolumeClaim (PVC)** | Um **pedido** de armazenamento: "quero 1 Gi, acesso ReadWriteOnce". |
| **StorageClass** | O "perfil" que sabe **criar PVs automaticamente** (provisionamento dinâmico). |

Fluxo:

```
PVC (pedido do aluno)
   │  StorageClass microk8s-hostpath
   ▼
PV (criado automaticamente)
   │
   ▼
Pasta no nó
```

O Pod **não conhece o caminho no nó**. Ele monta apenas o PVC:

```yaml
spec:
  volumes:
    - name: site
      persistentVolumeClaim:
        claimName: pvc-aluno07
```

Isso é o mesmo modelo usado em nuvem (EBS na AWS, disco persistente no GCP etc.). A diferença é que, no MicroK8s, o backend do `hostpath-storage` é uma pasta local do nó.

> **Importante:** `hostpath-storage` é ótimo para aprender o fluxo PV/PVC, mas **não é storage de produção**: não replica dados e não sobrevive à perda do nó. Em produção usa-se NFS, Ceph/Rook, Longhorn ou disco de nuvem. Este lab considera um cluster MicroK8s de **um nó**.

---

### 4. Ativando o hostpath-storage no MicroK8s

O add-on cria a StorageClass padrão `microk8s-hostpath`:

```bash
microk8s enable hostpath-storage
```

Conferir:

```bash
kubectl get storageclass
```

Saída esperada (o `(default)` indica que um PVC sem `storageClassName` usa essa classe):

```
NAME                          PROVISIONER            RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
microk8s-hostpath (default)   microk8s.io/hostpath   Delete          WaitForFirstConsumer   false                  10d
```

### 5. Roteiro Prático de Laboratório

Cada aluno usa o seu número: `aluno01`, `aluno02`, ..., `aluno20`. O roteiro é o mesmo; muda apenas o valor de `ALUNO`.

#### Passo A: Definir a variável do aluno

```bash
export ALUNO=alunoxx

echo $ALUNO
```

> Se abrir um novo terminal, execute o `export` novamente.
> Se `microk8s enable` pedir permissão, use `sudo microk8s enable hostpath-storage`.

#### Passo B: Limpar a aula anterior

```bash
kubectl delete deployment deploy-$ALUNO --ignore-not-found
kubectl delete configmap site-$ALUNO --ignore-not-found
kubectl delete pvc pvc-$ALUNO --ignore-not-found
```

> Apagar o PVC também apaga o PV e os dados. Aqui isso é intencional, para começar do zero.
> O template do Passo C já inclui o Service e o Ingress da aula anterior; se você os apagou, não tem problema. Se ainda existem, o `kubectl apply` apenas atualiza.

#### Passo C: Gerar o seu YAML a partir do template

O template `/tmp/storage.yaml` tem o PVC, o Deployment, o Service e o Ingress, separados por `---`. Ele usa a palavra **`nome`**:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-nome
  labels:
    app: app-nome
spec:
  storageClassName: microk8s-hostpath
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-nome
  labels:
    app: app-nome
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app-nome
  template:
    metadata:
      labels:
        app: app-nome
    spec:
      containers:
        - name: nginx-container
          image: nginx:latest
          ports:
            - containerPort: 80
          env:
            - name: ALUNO
              value: "nome"
          volumeMounts:
            - name: site
              mountPath: /usr/share/nginx/html/nome
      volumes:
        - name: site
          persistentVolumeClaim:
            claimName: pvc-nome
---
apiVersion: v1
kind: Service
metadata:
  name: svc-nome
  labels:
    app: app-nome
spec:
  type: ClusterIP
  selector:
    app: app-nome
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-nome
spec:
  ingressClassName: public
  rules:
    - host: curso.chr.eti.br
      http:
        paths:
          - path: /nome
            pathType: Prefix
            backend:
              service:
                name: svc-nome
                port:
                  number: 80
```

O que observar:

- `PersistentVolumeClaim`: pede **1 GiB** com acesso `ReadWriteOnce` (um nó lendo e escrevendo).
- `storageClassName: microk8s-hostpath`: usa o provisioner do add-on. Como essa classe é a default, o campo poderia ser omitido.
- `claimName: pvc-nome`: liga o volume do Pod ao PVC.
- `mountPath`: o PVC é montado em `/usr/share/nginx/html/nome`; o `index.html` fica dentro dessa pasta.
- `env ALUNO`: o valor `nome` vira o seu aluno; a página usa essa variável.
- `replicas: 1`: começamos com uma réplica porque o volume é `ReadWriteOnce`. Para bancos de dados com várias réplicas, o objeto correto é um `StatefulSet` (próximas aulas).
- `Service`: seleciona os Pods pelo label `app: app-nome` e expõe a porta 80 internamente.
- `Ingress`: roteia `/nome` no host `curso.chr.eti.br` para `svc-nome:80`. A pasta do site e o path do Ingress combinam.

> Se o seu `kubectl get ingressclass` mostrar `nginx` em vez de `public`, troque `ingressClassName: public` por `ingressClassName: nginx` antes de aplicar.

Gerar o arquivo do aluno:

```bash
cat /tmp/storage.yaml

sed "s/nome/$ALUNO/g" /tmp/storage.yaml > /tmp/$ALUNO-storage.yaml

cat /tmp/$ALUNO-storage.yaml
```

Verificar o conteúdo do YAML no site https://todiagram.com/editor (opcional).

#### Passo D: Criar os objetos

```bash
kubectl apply -f /tmp/$ALUNO-storage.yaml
```

Verificar:

```bash
kubectl get pvc pvc-$ALUNO
kubectl get pv
kubectl get deployment deploy-$ALUNO
kubectl get pods -l app=app-$ALUNO

kubectl get svc svc-$ALUNO
kubectl get ingress ingress-$ALUNO
```

O PVC deve estar `Bound` e o Pod `Running` (aguarde alguns segundos). Repare que a StorageClass usa `WaitForFirstConsumer`: o PVC só é vinculado depois que o Pod que o utiliza é agendado — por isso aplicamos o PVC e o Deployment juntos. Se quiser acompanhar:

```bash
kubectl get pods -l app=app-$ALUNO -w
```

(Ctrl+C para sair.)

Ver o PV que o provisioner criou e o caminho no nó:

```bash
PV=$(kubectl get pvc pvc-$ALUNO -o jsonpath='{.spec.volumeName}')
echo $PV

kubectl describe pv $PV
```

No `describe`, procure `Type: HostPath` e `Path:`. É a pasta real no nó — mas o Pod não precisa conhecê-la: ele usa o PVC.

#### Passo E: Criar o site dentro do volume

Agora vamos entrar no contêiner e criar o `index.html` **na pasta montada**:

```bash
POD=$(kubectl get pods -l app=app-$ALUNO -o jsonpath='{.items[0].metadata.name}')
echo $POD

kubectl exec -it $POD -- /bin/bash
```

Dentro do contêiner:

```bash
cd /usr/share/nginx/html/$ALUNO
ls -la
```

Crie a página (a variável `$ALUNO` vem do Deployment e `$HOSTNAME` é o nome do Pod):

```bash
cat > index.html <<EOF
<!DOCTYPE html>
<html lang="pt-BR">
<head>
  <meta charset="UTF-8">
  <title>$ALUNO</title>
</head>
<body style="font-family:sans-serif;text-align:center;margin-top:15%">
  <h1>$ALUNO</h1>
  <h2>Storage: hostPath + PVC</h2>
  <p>Criado em: $(date '+%d/%m/%Y %H:%M:%S')</p>
  <p>Pod: $HOSTNAME</p>
</body>
</html>
EOF

cat index.html
```

Saia do contêiner:

```bash
exit
```

> Tudo que foi gravado em `/usr/share/nginx/html/$ALUNO` está no volume, não no contêiner. A pasta do contêiner e o `Path:` do PV (visto no Passo D) são duas vistas do mesmo volume. É por isso que a página sobrevive quando o Pod é recriado.

#### Passo F: Conferir o Service/Ingress e testar

O template já inclui o Service e o Ingress (os mesmos da aula anterior). Como o novo Deployment usa o mesmo label `app: app-$ALUNO`, o Service seleciona os novos Pods — não use `kubectl expose`.

```bash
kubectl get svc svc-$ALUNO
kubectl get endpoints svc-$ALUNO
kubectl get ingress ingress-$ALUNO
```

Acesse (com a barra no final):

**https://curso.chr.eti.br/alunoxx/**

Deve aparecer o seu nome, a data/hora da criação e o nome do Pod.

#### Passo G: Provar que o volume persiste

Apague o Pod (o Deployment vai criar outro):

```bash
kubectl delete pod -l app=app-$ALUNO

kubectl get pods -l app=app-$ALUNO -w
```

Quando o novo Pod estiver `Running`, atualize a página:

- O nome do aluno e a **data de criação continuam iguais** (o arquivo não foi recriado).
- A linha `Pod:` mostra o nome **antigo**, porque foi o Pod antigo que gravou o arquivo.
- Compare com `kubectl get pods`: o Pod que está servindo agora é outro.

Agora apague o Deployment e recrie:

```bash
kubectl delete deployment deploy-$ALUNO

kubectl get pvc pvc-$ALUNO
kubectl get pv

kubectl apply -f /tmp/$ALUNO-storage.yaml
kubectl get pods -l app=app-$ALUNO
```

O PVC continua existindo e a página volta com o mesmo conteúdo. O ciclo de vida do volume é independente do Pod e do Deployment.

> **Cuidado:** se apagar o PVC, o PV e os dados também são apagados (a `RECLAIMPOLICY` da StorageClass é `Delete`). Só faça isso quando quiser apagar tudo.

#### Passo H: Remover após a validação

```bash
kubectl delete -f /tmp/$ALUNO-storage.yaml
```

Conferir:

```bash
kubectl get pvc
kubectl get pv
kubectl get pods -l app=app-$ALUNO
kubectl get svc svc-$ALUNO
kubectl get ingress ingress-$ALUNO
```

O `kubectl delete -f` remove o PVC, o Deployment, o Service e o Ingress; o PV é removido automaticamente pelo provisioner.

---

### 6. Resumo

| Conceito | Papel |
| --- | --- |
| `volumes` | Declara a origem do volume no Pod. |
| `volumeMounts` | Monta o volume em uma pasta do contêiner. |
| `hostPath` | Monta uma pasta do nó diretamente; simples, mas prende o Pod ao nó. |
| `PVC` | Pedido de armazenamento feito pela aplicação. |
| `PV` | Armazenamento real, criado pelo provisioner. |
| `StorageClass` | Define **como** os PVs são criados (no MicroK8s: `microk8s-hostpath`). |

**Regra prática:** para dados que precisam sobreviver ao Pod, use PVC — não grave dados apenas no sistema de arquivos do contêiner.

# Kubernetes: Service e Ingress — Publicando o Site

### 1. O caminho de uma requisição

Até agora acessamos o site por uma URL. Nesta aula vamos entender **quem faz o meio de campo** entre o navegador e o Pod:

```
Navegador
  │  https://curso.chr.eti.br/alunoxx/
  ▼
Proxy reverso (professor)
  │  encaminha para o Ingress Controller
  ▼
Ingress Controller (namespace ingress)
  │  regra: host curso.chr.eti.br + path /alunoxx → svc-alunoxx
  ▼
Service svc-alunoxx (ClusterIP)
  │  balanceia entre os Endpoints
  ├── Pod deploy-alunoxx-aaaaa
  ├── Pod deploy-alunoxx-bbbbb
  └── Pod deploy-alunoxx-ccccc
```

| Camada | Quem é | O que faz |
| --- | --- | --- |
| **Proxy reverso** | fora do cluster | Termina o HTTPS do domínio e encaminha para o Ingress Controller. |
| **Ingress** | objeto do Kubernetes | Roteia por **host** e **path** para um Service. |
| **Service** | objeto do Kubernetes | Dá um IP/DNS fixo e balanceia para os Pods. |
| **Endpoints** | gerado pelo Kubernetes | Lista de IPs dos Pods selecionados pelo Service. |
| **Pod** | menor unidade | Roda o nginx com o HTML. |

> O Pod muda de IP e de nome o tempo todo. O Service é o endereço estável; o Ingress é a porta de entrada HTTP.

---

### 2. Service: o endereço estável

Um Pod tem IP, mas esse IP muda quando o Pod é recriado. Se o navegador apontasse direto para o IP do Pod, o site quebraria a cada atualização do Deployment.

O **Service** resolve isso:

- Tem um **IP virtual fixo** (ClusterIP) e um **nome DNS** dentro do cluster.
- Seleciona os Pods por **labels** (`spec.selector`).
- Mantém a lista de **Endpoints**: os IPs reais dos Pods que estão prontos.
- Balanceia as conexões entre os Pods selecionados.

Tipos principais:

| Tipo | Para que serve |
| --- | --- |
| `ClusterIP` | Acesso **interno** ao cluster (padrão). É o que o Ingress usa. |
| `NodePort` | Abre uma porta em cada nó para acesso externo. |
| `LoadBalancer` | Pede um balanceador ao provedor de nuvem. |
| `ExternalName` | Aponta para um nome DNS externo. |

No nosso caso usamos `ClusterIP`: o proxy reverso chega no Ingress, e o Ingress chega no Service internamente.

#### O "expose" padrão em YAML

Na aula de Deployment usamos o comando:

```bash
kubectl expose deployment deploy-alunoxx --port=80 --target-port=80 --name=svc-alunoxx
```

O mesmo resultado, de forma declarativa, é este objeto:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: svc-nome
  labels:
    app: app-nome
spec:
  type: ClusterIP
  selector:
    app: app-nome
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
```

O que cada campo faz:

- `selector.app`: procura Pods com o label `app=app-aluno07`. Se o label não bater, o Service fica sem Endpoints.
- `port: 80`: porta do **Service** (a que o Ingress usa).
- `targetPort: 80`: porta do **contêiner** (onde o nginx escuta).
- `type: ClusterIP`: acesso interno, sem expor porta no nó.

Verificar:

```bash
kubectl get svc svc-$ALUNO
kubectl get endpoints svc-$ALUNO
kubectl describe svc svc-$ALUNO
```

O `get endpoints` mostra os IPs dos Pods. Se aparecer `<none>`, o Service não encontrou Pods: confira os labels e se o Pod está `Running`/`Ready`.

### 3. Ingress: a porta de entrada HTTP

O **Ingress** é um objeto que declara regras de roteamento HTTP:

- **host:** `curso.chr.eti.br`
- **path:** `/alunoxx`
- **backend:** `svc-alunoxx` na porta `80`

Quem obedece a essas regras é o **Ingress Controller** (no MicroK8s, instalado pelo add-on `ingress`). O proxy reverso do professor aponta para esse controller; o controller lê os objetos `Ingress` e encaminha cada path para o Service certo.

```
proxy reverso ──► Ingress Controller ──► Service ──► Pods
```

O Ingress sozinho não faz nada: ele precisa de um **Ingress Controller** rodando e de uma **IngressClass** válida.

No MicroK8s:

```bash
microk8s enable ingress
kubectl get ingressclass
kubectl get pods -n ingress
kubectl get svc -n ingress
```

> Em versões mais novas do MicroK8s o controller padrão é o Traefik e as classes podem aparecer como `public` (default), `traefik` e `nginx`. Use no template a classe que aparecer no `kubectl get ingressclass` — normalmente `public`. Em versões mais antigas, `nginx` também funciona.
> Em algumas versões o controller usa `hostPort` e não aparece como Service no namespace `ingress`; o pod do controller é o que importa.

#### O YAML do Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-nome
spec:
  ingressClassName: public
  rules:
    - host: curso.chr.eti.br
      http:
        paths:
          - path: /nome
            pathType: Prefix
            backend:
              service:
                name: svc-nome
                port:
                  number: 80
```

- `ingressClassName`: qual controller deve processar esta regra.
- `host`: o domínio que o proxy reverso encaminha (o proxy precisa preservar o cabeçalho `Host`).
- `path` + `pathType: Prefix`: tudo que começar com `/aluno07` vai para o backend.
- `backend.service`: o Service que recebe o tráfego e a porta dele.

Vários alunos podem ter objetos `Ingress` com o mesmo host e paths diferentes; o controller junta as regras. O que precisa ser único é o **path** (`/aluno01`, `/aluno02`, ...) e o nome do objeto (`ingress-aluno01`, ...).

Onde a página fica:

```
Ingress: /aluno07
   │
   ▼
Service: svc-aluno07
   │
   ▼
Pod: nginx
   └── /usr/share/nginx/html/aluno07/index.html
```

O path do Ingress e a pasta dentro do nginx precisam combinar. No nosso template o HTML é montado em `/usr/share/nginx/html/nome`, então a URL `/aluno07/` encontra `aluno07/index.html` sem precisar de rewrite.

### 4. O HTML no template: ConfigMap

Nas aulas anteriores a página era criada dentro do contêiner com `kubectl exec` ou com um `command` no Deployment. Agora vamos colocar o HTML **no próprio YAML**, usando um **ConfigMap**.

ConfigMap é um objeto para guardar configuração (texto, arquivos, variáveis) separado da imagem. O template terá:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: site-nome
  labels:
    app: app-nome
data:
  index.html: |
    <!DOCTYPE html>
    <html lang="pt-BR">
    <head>
      <meta charset="UTF-8">
      <title>nome</title>
    </head>
    <body style="font-family:sans-serif;text-align:center;margin-top:15%">
      <h1>nome</h1>
      <h2>Service + Ingress</h2>
      <p>Página criada junto com o Deployment.</p>
      <p>Service interno: http://svc-nome</p>
    </body>
    </html>
```

O Deployment monta esse ConfigMap em uma pasta do nginx:

```yaml
volumeMounts:
  - name: site
    mountPath: /usr/share/nginx/html/nome
volumes:
  - name: site
    configMap:
      name: site-nome
```

O `sed` que gera o arquivo do aluno troca `nome` também dentro do HTML, do nome do ConfigMap e do `mountPath`. Resultado: `site-aluno07`, `/usr/share/nginx/html/aluno07` e a página com o nome do aluno.

> ConfigMap é para configuração comum. Para senhas e tokens use `Secret`. Para dados que precisam persistir, use PVC (próxima aula).

### 5. Roteiro Prático de Laboratório

Cada aluno usa o seu número: `aluno01`, `aluno02`, ..., `aluno20`. O roteiro é o mesmo; muda apenas o valor de `ALUNO`.

#### Passo A: Definir a variável e conferir o Ingress

```bash
export ALUNO=alunoxx

echo $ALUNO

microk8s status --wait-ready
microk8s enable ingress

kubectl get ingressclass
kubectl get pods -n ingress
```

> Se `microk8s enable` pedir permissão, use `sudo microk8s enable ingress`.
> Se o add-on já estiver habilitado, o comando apenas confirma.

Guarde a classe que aparecer no `kubectl get ingressclass` (no laboratório usamos `public`).

#### Passo B: Limpar a aula anterior

```bash
kubectl delete deployment deploy-$ALUNO --ignore-not-found
kubectl delete service svc-$ALUNO --ignore-not-found
kubectl delete ingress ingress-$ALUNO --ignore-not-found
kubectl delete configmap site-$ALUNO --ignore-not-found
```

> O ConfigMap só pode ser apagado depois que o Deployment que o usa foi removido.

#### Passo C: Gerar o seu YAML a partir do template

O template `/tmp/service.yaml` tem quatro documentos separados por `---`: ConfigMap, Deployment, Service e Ingress. Ele usa a palavra **`nome`**:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: site-nome
  labels:
    app: app-nome
data:
  index.html: |
    <!DOCTYPE html>
    <html lang="pt-BR">
    <head>
      <meta charset="UTF-8">
      <title>nome</title>
    </head>
    <body style="font-family:sans-serif;text-align:center;margin-top:15%">
      <h1>nome</h1>
      <h2>Service + Ingress</h2>
      <p>Página criada junto com o Deployment.</p>
      <p>Service interno: http://svc-nome</p>
    </body>
    </html>
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-nome
  labels:
    app: app-nome
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app-nome
  template:
    metadata:
      labels:
        app: app-nome
    spec:
      containers:
        - name: nginx-container
          image: nginx:latest
          ports:
            - containerPort: 80
          volumeMounts:
            - name: site
              mountPath: /usr/share/nginx/html/nome
      volumes:
        - name: site
          configMap:
            name: site-nome
---
apiVersion: v1
kind: Service
metadata:
  name: svc-nome
  labels:
    app: app-nome
spec:
  type: ClusterIP
  selector:
    app: app-nome
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-nome
spec:
  ingressClassName: public
  rules:
    - host: curso.chr.eti.br
      http:
        paths:
          - path: /nome
            pathType: Prefix
            backend:
              service:
                name: svc-nome
                port:
                  number: 80
```

O que observar:

- **ConfigMap:** o HTML é criado junto com os outros objetos; não é preciso entrar no Pod para criar a página.
- **Deployment:** usa o label `app: app-nome` e monta o ConfigMap em `/usr/share/nginx/html/nome`.
- **Service:** seleciona os Pods pelo label e expõe a porta 80 internamente (`ClusterIP`).
- **Ingress:** roteia `/nome` no host `curso.chr.eti.br` para `svc-nome:80`.

Gerar o arquivo do aluno:

```bash
cat /tmp/service.yaml

sed "s/nome/$ALUNO/g" /tmp/service.yaml > /tmp/$ALUNO-service.yaml

cat /tmp/$ALUNO-service.yaml
```

Verificar o conteúdo do YAML no site https://todiagram.com/editor (opcional).

> Se o seu `kubectl get ingressclass` mostrar `nginx` em vez de `public`, troque `ingressClassName: public` por `ingressClassName: nginx` no template antes de aplicar.

#### Passo D: Criar os objetos e verificar

```bash
kubectl apply -f /tmp/$ALUNO-service.yaml
```

Verificar cada camada:

```bash
kubectl get configmap site-$ALUNO
kubectl get deployment deploy-$ALUNO
kubectl get pods -l app=app-$ALUNO

kubectl get svc svc-$ALUNO
kubectl get endpoints svc-$ALUNO

kubectl get ingress ingress-$ALUNO
```

O Pod deve estar `Running` e o `get endpoints` deve mostrar o IP do Pod. Se aparecer `<none>`, aguarde alguns segundos ou confira os labels:

```bash
kubectl get pods -l app=app-$ALUNO --show-labels
```

Se quiser acompanhar o Pod:

```bash
kubectl get pods -l app=app-$ALUNO -w
```

(Ctrl+C para sair.)

#### Passo E: Inspecionar Service, Endpoints e Ingress

```bash
kubectl describe svc svc-$ALUNO
kubectl describe ingress ingress-$ALUNO

kubectl get ingressclass
kubectl get pods -n ingress
kubectl get svc -n ingress
```

No `describe svc`, procure:

- `Selector`: o label que o Service procura.
- `Endpoints`: os IPs dos Pods encontrados.
- `Port`: porta do Service e `TargetPort` do contêiner.

No `describe ingress`, procure:

- `Host`: `curso.chr.eti.br`.
- `Path`: `/aluno07`.
- `Backend`: `svc-aluno07:80`.

O Ingress Controller é quem transforma essa regra em configuração de proxy. O proxy reverso do professor aponta para ele; por isso o site funciona de fora do cluster.

#### Passo F: Testar o Service por dentro do cluster

Antes de testar pela internet, teste o Service diretamente com um Pod temporário:

```bash
kubectl run teste-$ALUNO --rm -it --image=busybox:1.28 --restart=Never -- wget -qO- http://svc-$ALUNO
```

Deve aparecer o HTML da página. Isso prova que o DNS interno `svc-aluno07` e o balanceamento do Service estão funcionando, sem passar pelo Ingress.

#### Passo G: Testar pela URL pública

```bash
curl -s https://curso.chr.eti.br/$ALUNO/ | head

curl -s -o /dev/null -w "%{http_code}\n" https://curso.chr.eti.br/$ALUNO/
```

O código esperado é `200`. Se você acessar sem a barra no final, o nginx pode responder `301` para `/aluno07/`; use `curl -L` para seguir o redirecionamento.

Acesse também no navegador:

**https://curso.chr.eti.br/alunoxx/**

Deve aparecer o seu nome e o texto "Service + Ingress".

#### Passo H: Escalar e ver os Endpoints mudarem

```bash
kubectl scale deployment deploy-$ALUNO --replicas=3

kubectl get pods -l app=app-$ALUNO -o wide
kubectl get endpoints svc-$ALUNO
kubectl describe svc svc-$ALUNO
```

Agora o Service tem **3 Endpoints**. O `get pods -o wide` mostra os IPs dos Pods; compare com a lista de Endpoints. O Service balanceia as requisições entre eles.

Como a página é a mesma em todas as réplicas, o HTML não muda. O que prova o balanceamento é a lista de Endpoints acompanhando os Pods.

Volte para uma réplica:

```bash
kubectl scale deployment deploy-$ALUNO --replicas=1
```

#### Passo I: Apagar um Pod e acompanhar os Endpoints

Abra **dois terminais** (lembre do `export ALUNO=alunoxx` no segundo).

```bash
# Terminal 1 — acompanhar os Endpoints em tempo real
kubectl get endpoints svc-$ALUNO -w
```

```bash
# Terminal 2 — apagar um Pod
POD=$(kubectl get pods -l app=app-$ALUNO -o jsonpath='{.items[0].metadata.name}')
echo $POD

kubectl delete pod $POD
```

O IP do Pod apagado sai dos Endpoints; o Deployment cria outro Pod e o IP novo entra. O site continua no ar porque o Service aponta para os Endpoints atualizados, não para um Pod específico.

(Ctrl+C para sair do `-w`.)

#### Passo J: Remover após a validação

```bash
kubectl delete -f /tmp/$ALUNO-service.yaml
```

Conferir:

```bash
kubectl get pods -l app=app-$ALUNO
kubectl get svc svc-$ALUNO
kubectl get ingress ingress-$ALUNO
kubectl get configmap site-$ALUNO
```

O `kubectl delete -f` remove os quatro objetos do template: ConfigMap, Deployment, Service e Ingress.

### 6. Problemas comuns

| Sintoma | Causa provável | O que verificar |
| --- | --- | --- |
| `503 Service Unavailable` | Service sem Endpoints | `kubectl get endpoints svc-$ALUNO`, labels do Pod e status `Ready`. |
| `502 Bad Gateway` | Ingress não consegue chegar no Service | `port`/`targetPort` do Service e Endpoints. |
| `404` do nginx | Path do Ingress não combina com a pasta do HTML | `kubectl describe ingress`, `kubectl exec` e `ls /usr/share/nginx/html/alunoxx`. |
| `404` do Ingress Controller | Host/path não bateram | `kubectl describe ingress`, cabeçalho `Host` enviado pelo proxy. |
| Página padrão do nginx | ConfigMap não foi montado no lugar certo | `volumeMounts`, `mountPath` e `kubectl exec ... ls -la`. |
| Ingress ignorado | `ingressClassName` errada ou controller ausente | `kubectl get ingressclass`, `kubectl get pods -n ingress`. |
| `301` | URL sem a barra final | Use `/alunoxx/`. |

---

### 7. Resumo

| Camada | Objeto | Função |
| --- | --- | --- |
| Proxy reverso | fora do cluster | Termina o HTTPS e encaminha para o Ingress Controller. |
| Ingress | `Ingress` | Roteia host/path para um Service. |
| Service | `Service` | IP/DNS fixo e balanceamento para os Pods. |
| Endpoints | gerado | IPs dos Pods selecionados pelo Service. |
| HTML | `ConfigMap` | Conteúdo da página criado junto com o Deployment. |
| Aplicação | `Deployment`/Pods | nginx servindo a página. |

**Regra prática:** o Service é a porta estável da aplicação; o Ingress é a porta de entrada HTTP; os Pods vêm e vão, e os Endpoints acompanham. Na próxima aula vamos trocar o ConfigMap por um PVC para os dados sobreviverem ao Pod.


# Introdução ao Docker

## 1. História

O Docker surgiu em **2013** e ajudou a popularizar o uso de containers para executar aplicações de forma isolada e reproduzível.

A ideia de containers, porém, é anterior ao Docker. O Linux já possuía mecanismos para isolamento de processos e recursos, como:

- Linux namespaces
- cgroups
- LXC (Linux Containers)

O Docker facilitou a utilização desses mecanismos e criou um ecossistema baseado em imagens e containers.

```text
Imagem
   |
   v
Container
   |
   v
Aplicação
````

As imagens podem ser armazenadas e distribuídas através de registries, como o Docker Hub.

# 2. Teoria do Docker e Container

## 2.1 O que é um container?

Um container pode ser entendido como um **processo isolado dentro do sistema operacional**.

Ele utiliza o kernel do sistema operacional hospedeiro, mas possui uma visão isolada de diversos recursos.

Podemos representar:

```text
Sistema Operacional
|
+-- Processo A
+-- Processo B
|
+-- Container
    +-- Processo C
    +-- Rede
    +-- Sistema de arquivos
    +-- Hostname
```

Um container **não é uma máquina virtual**.

### Máquina virtual

```text
Aplicação
    |
Sistema Operacional convidado
    |
Hypervisor
    |
Sistema Operacional hospedeiro
    |
Hardware
```

### Container

```text
Aplicação
    |
Container
    |
Kernel Linux
    |
Sistema Operacional
    |
Hardware
```

Na máquina virtual existe um sistema operacional convidado completo.

No container, os processos utilizam o **kernel do sistema operacional hospedeiro**.

# 3. Como o Docker funciona — Namespaces

O isolamento dos containers utiliza recursos do próprio kernel Linux.

Um dos principais mecanismos utilizados são os **Linux namespaces**.

## 3.1 Principais namespaces

| Namespace | Função                                    |
| --------- | ----------------------------------------- |
| `pid`     | Isolamento de processos                   |
| `net`     | Isolamento da rede                        |
| `mnt`     | Isolamento dos pontos de montagem         |
| `uts`     | Isolamento do hostname                    |
| `ipc`     | Isolamento de comunicação entre processos |
| `user`    | Isolamento de usuários                    |

### PID Namespace

O namespace `pid` permite que o container tenha sua própria visão dos processos.

Um processo dentro do container pode possuir um PID diferente daquele observado no host.

### UTS Namespace

O namespace `uts` permite que o container tenha seu próprio hostname.

Podemos verificar o hostname do sistema:

```bash
hostname
```

Depois veremos o hostname dentro do container.

### Network Namespace

O namespace `net` é responsável pelo isolamento da rede.

Cada container pode possuir sua própria:

* interface de rede;
* configuração IP;
* tabela de rotas;
* interfaces virtuais.

Podemos observar as interfaces de rede do computador:

```bash
ip addr
```

Também podemos verificar as rotas:

```bash
ip route
```

Depois vamos comparar esses resultados com a rede existente dentro de um container.

# 4. Docker é efêmero

Uma característica importante dos containers é que eles devem ser tratados, normalmente, como **efêmeros**.

Um container pode ser criado, utilizado e posteriormente removido.

Os dados gravados diretamente na camada gravável do container não devem ser considerados permanentes.

Por exemplo:

```bash
docker run -it alpine sh
```

Dentro do container:

```bash
echo "Olá Docker" > arquivo.txt
```

Verificando o arquivo:

```bash
cat arquivo.txt
```

Saindo do container:

```bash
exit
```

O container poderá ser removido.

Quando um novo container for criado, o arquivo `arquivo.txt` não estará presente.

A ideia é:

```text
Container
    |
    +-- Executa a aplicação
    |
    +-- Pode ser removido
    |
    +-- Novo container pode ser criado
```

Para dados que precisam permanecer, utilizamos mecanismos específicos de persistência, como volumes.

## 4.1 Observando o isolamento da rede

Primeiro vamos observar a rede do computador:

```bash
ip addr
```

Observe as interfaces existentes.

Agora podemos verificar as rotas:

```bash
ip route
```

Vamos criar um container:

```bash
docker run -it alpine sh
```

Dentro do container:

```bash
ip addr
```

Depois:

```bash
ip route
```

Compare com os comandos executados no host.

A rede apresentada dentro do container é diferente.

Isso acontece porque o container está utilizando um **network namespace próprio**.

# 5. Executando um Nginx

Agora vamos executar nosso primeiro servidor Nginx utilizando Docker.

> **Importante:** todos os alunos estão utilizando o mesmo computador. Cada aluno deverá utilizar o número informado pelo professor no lugar de `nn`.

Por exemplo, se o professor informar o número `07`, o nome do container será:

```text
nginx07
```

## 5.1 Executar o container

Utilize:

```bash
docker run -d --name nginxnn nginx
```

Por exemplo:

```bash
docker run -d --name nginx07 nginx
```

Não vamos publicar nenhuma porta do container.

O Nginx será acessado diretamente de dentro do próprio container.

## 5.2 Verificar o container

```bash
docker ps
```

Podemos verificar que o container está em execução.

Também podemos consultar suas informações:

```bash
docker inspect nginxnn
```

Substitua `nginxnn` pelo nome utilizado.

---

## 5.3 Verificar o hostname

Vamos executar o comando `hostname` dentro do container:

```bash
docker exec nginxnn hostname
```

Também podemos entrar no container:

```bash
docker exec -it nginxnn bash
```

Agora:

```bash
hostname
```

O hostname visto dentro do container pertence ao ambiente isolado do container.

---

## 5.4 Verificar a rede do container

Dentro do container:

```bash
ip addr
```

Depois:

```bash
ip route
```

Compare os resultados com os comandos executados anteriormente no host:

```bash
ip addr
```

e:

```bash
ip route
```

Observe que o container possui uma visão própria da rede.

---

## 5.5 Testar o Nginx

Ainda dentro do container:

```bash
curl localhost
```

O comando acessa:

```text
localhost
```

Dentro do container, `localhost` representa o próprio container.

Como o Nginx está executando dentro dele, o resultado deverá ser a página HTML padrão do Nginx.

Também podemos verificar apenas os cabeçalhos HTTP:

```bash
curl -I localhost
```

O resultado deverá indicar que o servidor Nginx respondeu à requisição.
